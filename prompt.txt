## 2. 产品目标与不可更改规则

产品是面向大学生和研究生的校园兴趣社交与活动网站。

最终交付：通过手机和电脑普通浏览器访问的响应式 Web 网站，并具备真实的线上部署路径。

不是原生手机 App，不开发 APK/IPA，不要求应用商店安装。

保留四个一级模块，顺序固定：

发现 / 广场 / 信息 / 我的。

手机端保留底部导航，桌面端可以合理调整导航布局，但四个模块的名称、含义和顺序不变。

发现页必须保留：

- 找同频的人、找活动搭子两个并列入口；
- 其下横跨整行的星云探索入口；
- 星云进入独立页面，不把全站设计成星空风格。

Portrait 重点展示兴趣、自我表达和社交意图，而非颜值与照片。

星云维持开放的自由探索定位，并遵守 Portrait 公开可见性规则。

广场保留捞人、测评地图、吐槽、求助帖四类概念。

DEC-001：Portrait 认识同频的人、活动搭子与组队，是比赛优先完成的两条主流程。

DEC-002～003 的 Portrait 创建、预览、公开、撤回、定向可见与邀请接受规则，严格以决策日志为准。

## 4. 第一阶段开发边界

本阶段以交接文档的 T0、T1 为首要任务。

T0：检查朋友电脑上的 Node.js、npm、Git、项目目录和当前已有工程；提出技术选型，定义数据契约与模块文件所有权。

T1：建立能够真实启动的响应式 Web 项目，完成四栏导航、发现首页的三个入口、基础子路由及手机/桌面适配。

同时为后续 T2～T7 的 Portrait、活动、信息、星云和广场页面准备清楚的组件边界与导航结构，但不要在第一次执行中强行完成全部业务逻辑。

优先评估 React + Vite + TypeScript，并按需要使用 Tailwind、Lucide 等工具；这些仍是技术候选，而非团队已经正式选定的技术栈。

如原目录没有应用源码，建议在项目根目录下的 `app/` 中创建新工程，不要覆盖 `docs/`、原始 JSON、比赛说明及参考图片。

可使用合成数据，不得采集真实学生信息或擅自接入真实账号服务。

## 5. 任务与权限边界

WorkBuddy 是主体开发者，可以在已批准范围内创建工程、编写代码、安装必要依赖、运行测试和修复错误。

Codex 只负责辅助规划及审查，不由 Codex 代替主体编码。

未经确认不得：

- 增加真实登录、校园身份认证或实时聊天后端；
- 接入收费 API、云数据库或第三方服务；
- 决定活动自动审核、入队、名额占用或邀请拒绝规则；
- 将模拟聊天、模拟报名伪装成真实联网服务；
- 删除原有团队决策和设计参考文件；
- 在没有确认平台和账号权限时直接执行线上部署。

最终线上部署属于 T9，先记录构建与配置要求，待后续确认平台再实施。
